# OP 昵称入库前核对设计

## 目标

在账号写入 MongoDB 前，由服务端使用 OP卡密中的授权参数查询 QQ 用户资料。
API 返回成功时，`nickname` 是系统中 `OP名称` 的唯一可信来源；特定失败码按
业务规则调整售卖状态或追加备注。

本次覆盖：

- 后台手动新增账号
- Excel、XLS、CSV 批量导入中实际新增的账号

本次不覆盖：

- 后台编辑已有账号
- 重新检测抖音状态
- 批量导入选择“更新重复账号”后对已有账号执行的更新

重复账号更新属于已有数据编辑，不属于本次“新增入库前核对”范围。

## QQ OP 查询

服务端从 OP卡密中提取：

- 第 1 段：`openid`
- 第 2 段：`access_token`

请求：

```text
GET https://graph.qq.com/user/get_simple_userinfo
```

请求参数：

```text
access_token=<OP第2段>
oauth_consumer_key=1105602870
openid=<OP第1段>
```

请求只允许在 API 服务端发起。设置 5 秒超时，不自动重试。抖音账号检测和
QQ OP 查询互不依赖，手动新增或导入新增时并行执行，以免串行增加等待时间。

查询器设计为独立服务，并通过依赖注入提供给账号服务。测试使用假的查询器，
不访问真实 QQ 接口。

## 结果处理规则

### `ret = 0`

- `OP名称`强制改为 API 返回的 `nickname`
- 忽略 Excel 或手动表单中填写的 OP名称
- 保留原售卖状态

API 返回的昵称即使为空，也按 API 结果写入空字符串，不回退到提交值。

### `ret = -22`

- 保留提交的 OP名称
- 售卖状态强制改为“已停用”
- 不额外追加备注

### 其他 `ret`

- 保留提交的 OP名称
- 保留原售卖状态
- 把 API 的 `msg` 追加到备注，格式为 `OP: <msg>`
- 如果 `msg` 为空，追加 `OP: 未知错误`

### 无法取得有效 API 响应

下列情况继续入库，不把一次外部服务故障误判为 OP 无效：

- 请求超时或断网
- 返回非 JSON
- 响应结构无法解析
- OP卡密无法提取前两段

处理方式：

- 保留提交的 OP名称
- 保留原售卖状态
- 备注追加 `OP: 查询失败`

## 备注追加格式

不覆盖用户已有备注：

- 原备注为空：`OP: <消息>`
- 原备注非空：`<原备注> | OP: <消息>`

追加后仍服从现有备注最大长度限制。实现时应预留分隔符和 OP 消息所需空间，
对过长的原备注或 API 消息进行截断，保证最终值能通过共享数据校验。

## 与现有售卖状态规则的优先级

最终售卖状态按以下优先级计算：

1. 抖音账号状态为封禁时，永久锁定为“已停用”
2. QQ API 返回 `ret = -22` 时，设为“已停用”
3. 其他情况保留提交的售卖状态

因此任何 OP 查询结果都不能解除封禁账号的“已停用”状态。

## 数据流

### 手动新增

1. API 校验输入字段和 OP卡密时间戳。
2. 并行执行抖音账号检测和 QQ OP 查询。
3. 根据两项检测结果派生 `sec_uid`、账号状态、OP名称、售卖状态和备注。
4. 加密 OP卡密。
5. 创建 MongoDB 账号记录。
6. 写入审计日志，但不记录 OP卡密、Token、完整 QQ 请求 URL 或 QQ 原始响应。

### 批量导入

1. 预览阶段只解析和校验文件，不访问 QQ API。
2. 执行导入时，后台任务逐行处理。
3. 对实际新增的行调用与手动新增相同的账号创建流程。
4. 重复策略为“跳过”时不查询 QQ API。
5. 重复策略为“更新”时，更新已有记录但不触发本次新增核对。

将外部查询放在执行阶段，可避免预览成功后凭证状态发生变化，也避免用户只
预览不执行时产生无意义请求。

## 错误与安全处理

- QQ 查询失败不是整行导入失败；按上述备注规则继续入库。
- 抖音检测、数据校验、唯一索引和加密失败仍沿用现有错误行为。
- 只允许 HTTPS QQ API 地址。
- 不在日志、错误详情、审计记录或前端响应中包含 OP卡密、`openid`、
  `access_token` 或完整查询 URL。
- QQ 响应只保留业务需要的 `ret`、`msg` 和 `nickname`。

## 配置

Docker/API 环境增加：

```text
QQ_OP_PROFILE_API_URL=https://graph.qq.com/user/get_simple_userinfo
QQ_OP_APP_ID=1105602870
QQ_OP_PROFILE_TIMEOUT_MS=5000
```

API 地址必须为 HTTPS；AppID 为非空字符串；超时时间限制在合理范围内。

## 测试与验收

自动测试覆盖：

- 正确提取 OP卡密第 1、2 段并进行 URL 编码
- `ret = 0` 时 API 昵称覆盖提交的 OP名称
- `ret = 0` 且昵称为空时写入空 OP名称
- `ret = -22` 时强制“已停用”
- 其他 `ret` 时保留 OP名称和售卖状态，并追加 `msg`
- 其他 `ret` 且 `msg` 为空时追加“未知错误”
- 超时、断网、非 JSON、格式异常时追加“查询失败”
- 空备注和非空备注的追加格式
- 备注过长时安全截断
- 抖音封禁规则优先于所有 OP 结果
- 手动新增和导入新增共用同一规则
- 跳过或更新重复账号时不执行新增 OP 核对
- 日志和响应不泄露敏感 OP 参数

运行完整的 lint、类型检查、测试和构建，并使用 Docker 重建服务。最后通过
真实后台新增和导入各验证一条测试数据，确认 MongoDB 中的 OP名称、售卖状态
和备注符合规则，再删除测试数据。
